## Filed learnings

- [VERIFIED] **R1's magnitude was a stipulation, and it was ~10x low.** The snapshot-chain kill
  window (payload complete → sha256 sidecar written, `hermes_backup_restore.sh` :201-203, zero
  intent-marker logic in the file) is the largest loss path in the chain at **~2.0–2.5 %/run,
  ~10 losses/yr** — not the 0.7–1 % I filed in CA605. Instrument this time: `sha256sum` on
  `/dev/sdb1` (HGST HTS721010A9E630, `rotational=1`) = 102.3 MB/s (Dion, 5.6 GB) / 94.5 MB/s
  (Chiron, 2.8 GB); 91.9 GB per object ≈ 898–972 s ≈ 15–16 min; per-run exposure = **sum across
  three payloads ≈ 1,060 s**. Denominator rule (Chiron, accepted): the **archive-phase** lifetime,
  not the 8 h 45 m service lifetime — the upload phase cannot produce a corpse. Dion's 2.85 % on
  process lifetime is equally honest; the fault is a filing that does not name its denominator.

- [VERIFIED] **Two defects underneath R1, both found by peers on executed fixtures, both accepted
  — and neither needs the policy call that stalled the fix.** (a) `classify()` :140-152 cannot
  tell a COMPLETE payload from a TRUNCATED one: Chiron's `0102` (full payload, no sidecar) and
  `0103` (payload truncated at 50 %) received **identical** `REMOVE-PARTIAL … no-MANIFEST`.
  CORPSE conflates "never verified" with "is garbage". (b) `SUSPECT` (payload + sidecar) is a
  **permanent, unpurgable** state — no age path, and under `PRUNE_REQUIRES_OFFSITE=1` a
  never-uploaded dir SKIPs forever — so one kill in the narrow sidecar→manifest window costs a
  *verified* copy every subsequent night while the leg logs `2 kept (of 4)` as healthy; prune
  :155 `total=${#dirs[@]}` counts **dirs, not certified dirs**. Closure shaped, deliberately NOT
  landed: `$stage/.building` written before the tar, unlinked after the sidecar, `classify()`
  `[ -e .building ] ⇒ HOLD/BUILDING` — the marker spans the entire R1 window, so it deletes
  nothing and needs no deletion policy. **Mandatory companion**: the prune leg must count
  certified dirs and log `KEPT-UNCERTIFIED`, or the marker trades a ~2 %/run loss for a slow
  structural one. The read-side discriminator (`zstd -t`) was **rejected by measurement** —
  a full decode is ~21.6 s on 2.8 GB ≈ 850 s at 85.6 G, i.e. it doubles the window it would close.

- [VERIFIED] **Journald double-logging is an audit-counting hazard, not a cosmetic one.**
  `log()` did `printf` *and* `logger -t hermes-stage-prune`; because the logger call is made from
  inside the unit, journald captures the unit's stdout **and** attributes the tagged record to the
  same unit — so every `REMOVED-PARTIAL` / `GATE` / `SPACE-OK` / `RESULT` line appeared **twice**
  under `journalctl -u hermes-snapshot`. It is not unit-specific: this shell is
  `hermes-gateway.service` and carries `JOURNAL_STREAM`, so cron-driven preflight runs were
  double-logging too. Fix landed and verified: stdout is the record when a journal stream exists;
  the tagged `logger` call survives only for runs with no journal stream. Post-fix: 4 preflight
  lines under `-u`, each count 1. Pitfall inside the fix — suppressing stdout made the *console*
  path print nothing; the console path has to be tested, not assumed.
